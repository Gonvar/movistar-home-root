## Root cause of the write failure (settled offline)

Disassembly of `loot/kernel.elf`:

**The iterator does NOT cache `iov_base`.** `copy_page_to_iter`'s inner loop
reloads it every segment:
```
c020138c: ldr r8, [r7, #0x8]   ; iov->iov_base, fresh each pass
c02013d8: add r7, r7, #8       ; advance to next iovec
c02013e8: b   c0201360
```
So the self-overwrite IS visible to seg12. Caching was never the bug.

**`i->count` is a hard ceiling**, decremented per byte:
```
c0201548: ldr r2, [r5, #0x10]   ; count
c0201578: str r3, [r5, #0x10]   ; count -= copied
```
and `rw_copy_check_uvector` sums all `iov_len` into it at import (`c0222fc0`).

=> With `iov[10].iov_len = 65536` at import, the entire budget is spent draining
seg10 and seg12 can never run, regardless of redirect. This explains why both a
bogus and a valid target returned the identical count.

**`__check_object_size` cannot silently drop.** On failure it calls `printk` then
`udf #0x12` (panic) — `c02201a0`/`c02201a4`. So a clean run (no reboot) implies
the check passed.

## The corrected port and its result (JOB-74/76/77)

Reference PoC: <https://github.com/wired0ut/CVE-2019-2215>

Three bugs were fixed relative to our earlier harness:
1. **Threading model** — victim must be a pthread in the SAME process (not
   `fork`), so the DEL corruption hits the same mm that owns the iovec array.
2. **Pre-advance** — `iov[10].iov_len = 1` satisfied by a pre-written byte, so
   the iterator parks on seg11 *before* the UAF with its budget intact.
3. **arm32 sizing** — iovec fields are 4 bytes, so covering
   `iov[10].len .. iov[12].base` is `0x10`, not `0x20`.

JOB-76 added an honest baseline: with no DEL the counts were `5` and `17`
(exactly `1+len`), proving the harness reports faithfully. With DEL the counts
became exactly `1+0x10+len` — all three segments ran.

## The measurement that settled it (JOB-78)

Rather than infer, JOB-78 gave each segment a distinct *userspace* destination
and pattern:

```
BUF_A = 0x11   segment 10 ran
BUF_B = 0x66   segment 11 ran to USERSPACE, not to the kernel array
BUF_C = 0x22   segment 12 ran to USERSPACE
```

**seg11 executed with its original userspace base.** The self-overwrite never
happened. So the redirect was never installed, and every "full count" was still
just userspace traffic.

Root cause: the victim consumed all pending socket bytes in a **single**
`copy_page_to_iter` pass, so `iov[11].base` was read *before* the DEL had
landed. The per-segment reload (`c020138c`) only takes effect across
**separate** kernel copy-loop entries — i.e. the victim must actually return to
userspace and block between segment 10 and segment 11.

JOB-77's split-send attempt failed because the socket coalesced the writes, so
both landed in one pass. JOB-79 (`poc-wq`) tried the reference's 3s `SYNC_WAIT`
to force a genuine block — and took the device down with it.

## Honest assessment

We have a **working, reproducible kernel read** and a **write primitive that is
blocked on one precise, understood condition**: the victim must be parked in
`recvmsg` with an empty socket *before* the DEL, so the self-overwrite is
observed by a fresh copy loop.

The irony worth stating plainly: JOB-79's crash may mean the 3s wait finally
*did* make the redirect land — i.e. the write may now work. That is also why it
is dangerous to simply retry: the "valid" target in those runs was
`init_task.comm`, right next to kernel text.

Progress is real but far slower than the earlier notes claimed, because those
notes rested on an invalid success signal.

## Verified address map (from disassembly, this exact kernel)

Confirmed by reading the syscall paths directly, not inferred from struct guesses:

```
thread_info + 0xC  -> task_struct          (sys_getuid: ldr r3,[r3,#0xc])
task_struct + 0x4B0 -> real_cred           (get_task_cred: ldr r4,[r5,#0x4b0])
task_struct + 0x4B4 -> cred                (commit_creds: ldr r4,[r6,#0x4b4])
init_task        = 0xC1413738
init_cred        = 0xC14194F8
```

`cred` id block — NOT contiguous:

| Field | Offset | Source |
|---|---|---|
| uid  | cred+0x04 | `c0135e74: ldr r0,[r3,#0x4]`  |
| gid  | cred+0x08 | `c0135ecc: ldr r0,[r3,#0x8]`  |
| euid | cred+0x14 | `c0135ea0: ldr r0,[r3,#0x14]` |
| egid | cred+0x18 | `c0135ef8: ldr r0,[r3,#0x18]` |

`sys_getuid` also shows the overflow-uid idiom: if `uid == -1` it substitutes
`overflow_uid` (`c1418e18`).

**Safety consequence:** the four id fields are split across a 0x10 gap, so a
blind contiguous write across them would corrupt whatever lives in between.
Any future cred patch must target the exact fields, not a block assumption.

## Write-primitive status (JOB-81 / 83 / 84)

All runs fault-probe only: a single round, ONE deliberately-unmapped target
(`0xDEADC0DE`). Faulting on unmapped memory returns a short `readv` via the
usercopy exception table — it cannot corrupt the kernel. The device has stayed
healthy through every run.

### What is now proven
- The victim genuinely **blocks in the kernel before the DEL**: JOB-83 sampled
  its `/proc` state 20/20 times as `S` (sleeping). Ordering is correct.
- The corruption mechanism still lands (leak path confirms the self-pointer twin
  at `array+0x54`, and JOB-80 re-confirmed it on the recovered device).

### What is still not working
`seg11` executes with its **userspace** base, so the self-overwrite never writes
into the kernel iovec array and `seg12` is never redirected.

Instrumentation (distinct user buffers per segment):
```
BUF_B[0]=00   seg11 wrote o11 into the USER buffer, not the kernel array
BUF_C[0]=ef   seg12 wrote the payload into the USER buffer
BUF_A[0]=ee   seg10's buffer untouched (memset ran after its write)
readv=21      always exactly 1+0x10+4
```

The full count is still meaningless as a success signal — it just means the
socket delivered 21 bytes into userspace buffers.

### Bugs fixed along the way
1. fork -> same-process pthread victim (DEL must hit the same mm).
2. Pre-advance seg10 (iov[10].iov_len=1 + 1 pre-written byte) so the iterator
   parks on seg11 before the UAF.
3. arm32 iovec field size: 4 bytes, so the self-overwrite spans **0x10**, not 0x20.
4. Missing post-import spray (added in fp4; did not change the outcome).
5. `pthread_t` is not a tid — the block-detector needed `syscall(SYS_gettid)`.

### The open question
The iterator reloads `iov_base` per segment (confirmed at `c020138c`), and the
victim is provably parked when the DEL fires, yet seg11 still sees its original
userspace base. Either:
- the victim's iovec array is NOT the object the DEL corrupts (reclaim landed on
  a different slab object despite the spray), or
- the corruption offset is not `array+0x54` for this iovec geometry.

Both are answerable **offline / with one instrumented run** by reading the
victim's array back after the DEL and checking whether `iov[11].base` actually
holds the self-pointer. That single measurement will discriminate the two.
