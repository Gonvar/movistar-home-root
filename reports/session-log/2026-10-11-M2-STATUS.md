# CVE-2019-2215 M2 — Exploit Status (2026-10-11, JOB-41..59)

Target: Movistar Home RG3205W (ASKEY), Android 8.1, arm32, kernel 3.18.71-perf (msm8953).
Actor: untrusted_app (Termux, uid 10042). Software-only. No OTA/firmware, no factoryreset.

## VERDICT (live-confirmed)
CVE-2019-2215 (Bad Binder) is present and unprivileged-triggerable on this device:
the 3.18.71 backport took `synchronize_rcu` but dropped the `wake_up_poll(POLLFREE)`
base fix, leaving the epoll-pwq entry dangling across `BINDER_THREAD_EXIT`.

## M2 — what WORKS (receipts, JOB-41..59)
1. **UAF trigger** (M1, JOB-41): open /dev/binder, BINDER_VERSION (protocol 7),
   epoll ADD (binder_thread created), BINDER_THREAD_EXIT (free with pwq linked),
   epoll DEL → stale remove_wait_queue on freed memory. Exit 0, device stable.
2. **Reclaim + corruption** (JOB-49..59, ~100% reliable):
   - freed binder_thread (308B → kmalloc-512) reclaimed by a forked victim's
     writev iovec import (kmalloc(64*8) = 512B, LIFO freelist).
   - DEL's remove_wait_queue → spin_lock cycles the lock word at +0x50
     (= kiov[10].base, junk-region value X*0x10001 → (X+1)*0x10001),
     list_del writes task_list self-pair at +0x54/+0x58
     (= kiov[10].len, kiov[11].base ← &task_list = array+0x54).
   - **TRUE geometry (live-derived, corrects earlier disasm read by 4):**
     wait.task_list = {next@thread+0x54, prev@thread+0x58}; array = twin−0x54
     (always 0x200-aligned ✓). Only kiov[11].base is corrupted; seg11.len is
     left untouched, so the victim copies a user-chosen length from array+0x54.
3. **Kernel physmap read (arbitrary length, forward windows)**:
   - victim writev imports seg11 = {scratch, N}; after corruption it copies N
     bytes from array+0x54 through the pipe to us. N up to 8MB per round
     (JOB-56..59). Page-aligned N (multiples of 0x1000) is CRITICAL: with
     F_SETPIPE_SZ(0x1000) the pipe has one buffer slot; a partial tail can
     never be written once the previous chunk packs the page (victim wedges in
     pipe_wait forever — root cause of the JOB-50..51 failures).
   - Receipts (JOB-59): 8MB window read at 0xd88d2254..; found real
     task_struct `TASK @ 0xd8bdf700: pid=2271 comm=p0...` (signature:
     pid@+0x3C8 == tgid@+0x3CC, group_leader@+0x3EC == &task).
   - Sprayed binder_procs in the dump give our own task_struct pointer
     (candidate = proc+0x24 group_leader; e.g. 0xd758f000, stable per run).
   - Array slab steering: 220 held binder procs + up to 760 held epolls
     (eventpoll ≈ 464B → kmalloc-512) drain the freelist cluster and force
     the array into fresh/node-partial slabs (observed clusters: 0xd1db/0xd1dc
     (31MB), 0xd751, 0xd763, 0xd88d (649MB), 0xe4db, 0xe89, 0xea2e).
4. **Infra**: gzipped 36KB payload (1.75MB→36KB via -Wl,--strip-all+gzip), md5
   verified per job; orphan-victim purge (pkill) before each run; alarm(200)
   watchdog; WNOHANG teardown poll (400ms) before SIGKILL; device-side
   poller survived all runs (no wedges since JOB-45).

## M2 — what is DEAD and why (the key discovery)
**All usercopy kernel-write primitives are blocked on this kernel.**
`copy_page_to_iter` (the readv/pipe-read copyout path) at c02011c8 contains:
- a **user-write probe**: `strbt r3=0, [dst]` under a DACR domain-dance
  (mrc/mcr p15 c3 c0: set domain1=client), with fixup → EFAULT path, for
  BOTH the first and last destination byte;
- `__check_object_size` (CONFIG_HARDENED_USERCOPY) before every
  `arm_copy_to_user`.
Kernel pages are AP=01 (privileged-only), so user-mode stores (strbt) to any
kernel address fault → the copy is silently dropped. Meanwhile the copyIN
path (writev/pipe_write, `copy_page_from_iter` c0200630 → plain arm_copy_from_user,
no PAN, no probe) reads kernel addresses fine — hence:
- writev victim = **reads kernel fine** (our leak works),
- readv victim = **cannot write kernel** (every kwrite/kread-redirect fails).
Live confirmation (JOB-55): the readv round's ajunk copy (which must land at
array+0x54 to install the kiov[12].base redirect) is dropped even when the
final payload destination is a plain user address → redirect never installs.
Therefore: **addr_limit clobber, cred patching, selinux_enforcing — every
classic endgame that needs a kernel write via the corrupted iovec — is closed.**

Also confirmed dead: the spinlock +0x10001 increment cannot lift a base out
of user range (import-time access_ok caps seg bases at 0xBF000000), and
list_del writes are fixed self-pair values at the freed slot only.

## Remaining attack surface / endgame options
A. **arm32 vectors page (0xFFFF0000)**: if any kernel page is mapped
   user-accessible (AP=11), the probe would pass there. Vectors page /
   kuser helpers (0xFFFF0F60..0xFFFF0FF8) are the classic candidates.
   Test = a readv round targeting 0xFFFF0000 (probe-only first; an actual
   vector overwrite crash-risky, power-cycle recovery).
B. **Wait-queue entry forging**: fake wait_queue_entry inside our iov array
   (fully controlled contents; func = kiov[13].base field, unconstrained!)
   triggered by a wake on a queue whose head points into the array. Requires
   finding a live-object reclaim chain where the +0x54/+0x58 self-pair
   poisons a non-empty list into a walkable state. Research needed.
C. **kgsl-3d0** (openable from Termux, root-writable ioctls): separate
   attack surface on file as backup.
D. **Accept read-only**: physmap disclosure of task/cred contents is already
   a significant result on a locked consumer device.
