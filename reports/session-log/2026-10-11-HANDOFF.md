## 1. Read this first

Two claims from earlier in this session were **wrong** and are retracted:

- **"Arbitrary kernel write proven" (M3/M4) — RETRACTED.** The `readv` full-count
  signal is circular. JOB-71 proved it: a bogus `0xDEADC0DE` target also returned
  a full count, because seg12 fell back to the userspace `scratch` buffer.
  Full count ≠ kernel write.
- **M2's "read-only dead end" verdict — RETRACTED.** There is no PAN/uaccess
  gate in the copyout path. `__check_object_size` only panics on failure.

Also: any run described as "safe by construction" was mis-described. The fault
probe's *target* is harmless, but the UAF that sets it up is inherently
destabilising and has taken the device down twice (JOB-79, JOB-83).

## 2. Where things actually stand

**Proven:**
- Forward read leak from the imported iovec array works and is re-confirmed

- The victim genuinely **blocks in the kernel before the DEL** — JOB-83 sampled

- `sizeof(struct binder_thread) = 412` → **kmalloc-512** (kernel `c08e6e50`:
  `mov r2, #412` before `kmem_cache_alloc_trace`).

**Not working:** the self-overwrite. `seg11` still executes with its userspace
base, so `iov[11].base` is never redirected.

**Root: not achieved.**

## 3. The root cause found (this is the important finding)

The write rounds used `NUM_IOVECS 24`. On arm32 `sizeof(struct iovec) == 8`:

| import | bytes | SLUB cache |
|---|---|---|
| `binder_thread` | 412 | **kmalloc-512** |
| 64 iovecs × 8 | 512 | **kmalloc-512** ✓ |
| 24 iovecs × 8 | 192 | kmalloc-256 ✗ |

The 24-iovec rounds allocated into a **different cache** than the object they
needed to reclaim. The reclaim was structurally impossible — not timing, not a
race, not a spraying problem. This retroactively explains every prior
"seg11 wrote to userspace" result in one line.

**The fix (`NUM_IOVECS 64`) is compiled, staged, and has never executed once.**
Do not describe it as working. Verify it on the wire first.

## 5. If the write proves out

1. Spray binder_procs, read one with `tgid == getpid()`.
2. Read its `group_leader` → that is our own `task_struct`, set by the kernel at
   `open()` time.
3. Patch `real_cred` (`+0x4B0`) and `cred` (`+0x4B4`) with `init_cred` —
   adjacent, so one 8-byte write.
4. `getuid() == 0`.

**Verify the target before writing.** Read it back and confirm `comm` matches
`/proc/<pid>/comm`. An 8-byte write to an address that isn't a `task_struct` is
an oops. If the confirmation is ambiguous, **report and stop** — do not push.

Address map (verified from syscall paths):
`thread_info+0xC`→task · `task+0x4B0`→real_cred · `+0x4B4`→cred ·
`cred+0x04` uid · `+0x08` gid · `+0x14` euid · `+0x18` egid ·
`init_task=0xC1413738` · `init_cred=0xC14194F8`

**Never point the primitive at `init_task` or near kernel text.** JOB-79 did
exactly that and took the box down.

Caveat to state plainly if root lands: `init_cred` does not survive reboot,
leaves `real_cred != cred`, and does nothing for SELinux or the app UID mapping.
It is a working root shell, not persistence.

## 6. Discipline rules (learned the hard way)

- **Never `pkill`/restart `upload_server.py`.** It's launchd-managed. Health-check
  with `lsof -nP -iTCP:8010 -sTCP:LISTEN`; restart only if genuinely absent.
- **One run at a time. Wait for the result before building the next binary.**
  Ten builds a minute told us the same thing ten times and cost us the device.
- **Editing `job.sh` re-triggers a full download-and-execute on the router**
  (the poller runs it every ~15s). That churn is the real cost, not the pkill.
- Keep the server whitelist pointed at a harmless binary so an idle poll cycle
  does nothing.
- If the reclaim is still not working, the next step is the **array read-back**
  (read the victim's array after the DEL, check whether `iov[11].base` actually
  holds the self-pointer). One measurement, discriminates object-vs-offset.
  Don't guess again.
